# Working on the Leon Gold sync server

- The owner writes in Persian and uses an iPhone. Reply in Persian.
- This holds the ledger's live business data. Ask before anything that deletes or rewrites stored data; test before every deploy.
- `data/` (the SQLite database and its daily backups) is never committed.

## What it is

One shared copy of «دفتر لئون»'s data for every device. The ledger still works offline from its own IndexedDB; `../leon-gold/offline/runtime.js` queues each change in an outbox, pushes it here, and pulls everyone else's changes. The last change to reach the server wins per document; a document with an unsent local change is never overwritten by a pull.

- `server.mjs`: plain `node:http` + `node:sqlite`, no dependencies (Node 24+).
- Tables: `docs (col, id, data, rev)` where `data` NULL = deleted, `blobs` (product photos), `users` (scrypt), `sessions` (sha256 of the token, 180 days), `meta.rev` (one counter for every change).
- API: `POST /api/login {u,p,device}` → `{token}`; then with `Authorization: Bearer`: `GET /api/state`, `GET /api/pull?since=rev`, `POST /api/push {changes:[{c,id,d|null}]}`, `PUT|GET /api/blob/:id`, `POST /api/logout`. A `/daftar` prefix is accepted, for when the ledger and API share one domain.
- Persian digits in usernames and passwords count as Latin ones (the phone keyboard types either).
- A new device can also sign in with the ledger's own sign-in users (`settings/lock`, synced like any doc: name + numeric password, `sha256(salt|digits)` as `pinHash()` in the ledger, or its FNV fallback). It gets an owner session (`user` = SETUP_USER), since the ledger is the owner's alone (owner, 2026-10-31).

## «حساب من»: the customers' and suppliers' panel (`portal.mjs`)

- Read-only window for each party onto its own share of the ledger, shown by the site at `/hesab/`. It never writes ledger data (its only write is a pending receipt, below). Its own tables (`portal_logins`, `portal_invites`, `portal_sessions` 30 days, `portal_receipts`); a portal token never opens the sync API and an owner token never reads `/api/portal/me`. No SMS (owner, 2026-10-31).
- Sign-in by username + password: the owner sets them per party in the ledger's «کاربران» (`GET /api/portal/logins` → `{logins:[{partyId, username}]}`; `POST /api/portal/login/set {partyId, username, password}`; `POST /api/portal/login/remove {partyId}`; ledger token). Username 3–40 of a-z 0-9 . _ -, password at least 6; Persian digits count as Latin, usernames ignore case; scrypt hashes on the server only, never synced, never in the off-site copy, never sent back. A new password or removal signs the party out everywhere; a rename alone does not. The party: `POST /api/portal/login {u, p}` → `{token}`; it changes its own password and/or username with `POST /api/portal/password {old, new?, username?}` → `{ok, username}` (portal token; a new password signs its other devices out, this one stays; `bad_old`, `bad_username`, `username_taken`, `nothing`, `no_login` when it came in by link only); `/api/portal/me` accounts carry the party's `phone` for the profile; `/api/portal/me` carries `username` when it has one; 10 wrong tries per address and 10 per username in 15 minutes → 429.
- One-time link: the owner (ledger token) `POST /api/portal/invite {partyId}` → `{link}` (7 days, one use, a new one cancels the old); `POST /api/portal/redeem {k}`. `POST /api/portal/revoke {partyId}` signs that party out everywhere.
- Rules and details: `POST /api/portal/terms/accept {text,label}` keeps the exact text once by its SHA-256 (`portal_terms`) and each acceptance with server time, IP and browser (`portal_accepts`) as the party's electronic signature; `POST /api/portal/info` stores the party's own optional details (`portal_info`, fields in `INFO_FIELDS`); `/api/portal/me` returns `terms` (last signature) and `info`; the owner reads both with `GET /api/portal/party?id=`. «حساب من» asks again whenever the rules text changes. `test/terms.test.mjs`.
- `GET /api/portal/me`: balances and statement worked out exactly like the ledger's `compute()` (positive = the party owes Leon). Customers get their orders without the workshop; suppliers get the open order items with their `supId`, without the customer. Invoice statement entries carry their printed `lines` (desc/qty/weight/carat/amount or totalG), same as the ledger's own invoice view. They also carry `sheet` (`sheetOf()`): the saved invoice's printed parts (sheet inputs `vals`, rows, gold, trade, transfer by name) for the ledger's own A4 sheet, which «حساب من» opens in the ledger's «#view» mode, so the party sees exactly the owner's invoice. The trade's rial entry carries the same `sheet`. `test/sheet.test.mjs` checks what is left out. An order/work item carries its product's own photo (a blob id) when the product has one. Never sent: settlement notes, purchase wage (`costAj`), product ids, or anything that is not on the printed invoice. `test/portal.test.mjs` checks each of these.
- `GET /api/portal/photo/:id` (portal token): a line item's product photo, or the caller's own receipt photo (below) — served only when it is actually theirs, else 404; never a public URL.
- `POST /api/portal/receipt {image, amount?, date?}` (portal token, a customer party): a photo of a card-to-card transfer receipt (`image` a `data:image/...;base64,` URL), stored PENDING and touching no balance — the owner later records the real document in the ledger by hand and marks it done. Limits: images only, 8MB after decoding, 8 uploads a day per party. `GET /api/portal/receipts` / `POST /api/portal/receipt/:id/done` (owner, ledger token) list and close them. `GET /api/portal/receipts/mine` (portal token): the party's own receipts (id, blob, amount, date, ts, status), so «حساب من» shows which Leon has recorded.
- A party with `portalOff: true` on its ledger card has no «حساب من»: its password no longer signs in, invite and redeem answer 403 `portal_off`, an open session reads nothing (403). The ledger's owner-only «کاربران» sets it (and calls revoke); invites, revoke and closing receipts are made only there, never from a public page.

## «روتین من»: the owner's personal routine app (`gym.mjs`, page in `gym/`)

- Not business: the owner's own training / diet / sleep routine, and people they invite. Page at `/gym/` (copied from `projects/leon gym/app/` — moved out of LEON PROJECT on 2026-11-16, at `../../../leon gym/app/` from here — which is where it is edited; copy `index.html`, manifest and icons here before committing). API `/api/gym/*`.
- Own tables `gym_users` (scrypt, role admin|user), `gym_sessions` (365 days), `gym_data` (one JSON document per user, `rev`; a PUT names its `base` rev, a stale one gets 409 + the current copy and the page merges), `gym_files` (images/PDF, 6MB, per user). A gym login never opens the ledger and a ledger session never opens the gym (`test/gym.test.mjs`).
- The first admin `leon` is made on an empty `gym_users` (hash in `gym.mjs`). Admins add users, reset passwords (data kept) and remove users from the page's «مدیریت».
- Wrong logins: 10 per address, 20 per username in 15 minutes. `gym_users`/`gym_sessions` are dropped from the off-site copy; `gym_data`/`gym_files` are backed up with everything else.
- Reading uploads: `POST /api/gym/extract {kind: tests|diet|supp|workout, text, images[≤6 data:image]}` → `{result}` (JSON the page shows for review before saving). It calls an OpenAI-compatible service set in the Liara panel: `GYM_AI_URL` (base, before `/chat/completions`), `GYM_AI_KEY`, `GYM_AI_MODEL` (default `openai/gpt-4o-mini`, Liara AI's naming; must read images). The server is in Iran, so the service must answer Iranian servers (e.g. Liara's own AI). Unset → 503 `ai_off` and `/api/gym/me` says `ai:false`; the page then still reads text-layer InBody PDFs on the phone. 40 reads per user per day. `pdf.min.js` / `pdf.worker.min.js` (pdf.js 3.11.174) are served from `gym/`.

- Reminders («یادآورها», Web Push, same VAPID keys as `notify.mjs`, which exports `sendPush`/`okEndpoint` for this): a phone subscribes with `POST /api/gym/push/sub {endpoint, keys}` (table `gym_push_subs`, 10 per user; `/unsub`, `/test`, `GET /push/key`). The page works out the next 8 days' timed steps (its choices in the synced `notify` section: kinds, minutes early; ticked steps skipped) and sends them whole with `PUT /api/gym/push/plan {items:[{at, tag, title, body}]}` (replaces the user's schedule; `gym_push_plan`, ≤400, ≤16 days ahead). A ticker (`GYM_PUSH_TICK_MS`, default 30 s) sends what is due to that user's phones only; more than 15 minutes late is dropped. `gym/sw.js` (served no-cache) shows them. iPhone: only from the home-screen icon. Both tables are left out of the off-site copy. `test/gym-push.test.mjs`.
- «غذاها» (diet food explorer): the dishes and their per-100 g ingredient values live in the page (`DISHES`, `ING`); every number is computed from the ingredient weights. The server only counts, shared by all users: `POST /api/gym/foods/mark {id, kind: view|cook, undo?}` (one per food, user, kind and Tehran day; table `gym_food_marks`), `GET /api/gym/foods/stats` → `{foods: {id: {views, cooks, myCooks}}, cookedToday}`. `test/gym-foods.test.mjs`. Its photos are `gym/img/<id>.jpg` (Wikimedia Commons, free licences; credits in the page's `PHOTOS` and shown under «غذاها»); `page()` serves that one sub-folder. «پیشنهاد برای تو» (per user, in the page): for each meal of the day a dish of about the same calories, with the portion to eat; «کمک‌رژیم»: snack swaps with amounts.
- Recipes: the page's `RECIPES` (matched by menu name) give a light way to cook each menu with prep and cook times; no server part.

## Backups

- On the server: `data/backups/leon-YYYY-MM-DD.db`, last 30 kept. Same Liara disk, so it does not survive losing the disk.
- Off-site: `GET /api/backup` (owner token) sends a fresh copy without `users`, sessions, party logins or links. `tools/backup.mjs pull` on the owner's PC saves it to `LEON PROJECT\backups` (outside every repo), checks it (`PRAGMA integrity_check`), keeps 60. The token lives in `~/.leon-backup.json` (`os.homedir()`: `$HOME` on the Mac, `%USERPROFILE%` on Windows) after a one-time `node tools/backup.mjs login` (needs the ledger password; the owner does it). Mac (now): the daily `Leon company/Backup/leon-backup.sh` (launchd 13:00) runs `pull` with `LEON_BACKUP_DIR=Leon company/Backup/server` whenever that token file exists, and logs a skip otherwise. Old PC: a Windows task «Leon Gold backup» ran it daily.
- Restore: `node tools/backup.mjs restore <file> --to <url> --yes` writes the copy back through the normal API (documents the copy lacks are deleted; devices then pull the result). Always try it first on a throwaway local server (`DATA_DIR=<temp> node server.mjs`, `node admin.mjs user ...`), and ask the owner before running it against the live server. `test/backup.test.mjs` runs backup → change → restore end to end.
- Photos are served only as image types (anything else as `application/octet-stream`) with `CSP: sandbox`; unexpected errors answer `{error:"server"}` and stay in the log.

## Run and test

- `npm test` (node --test). The two-device browser test lives in the ledger: `node ../leon-gold/tests/sync.test.mjs` (build the ledger first).
- Local: `node server.mjs` (port 3000, data in `./data`). Users: `node admin.mjs user <name> <password>`; `node admin.mjs state`.
- Env: `PORT`, `DATA_DIR`, `ALLOWED_ORIGINS` (comma list; default `https://leon-gold.github.io,https://leongold.net,https://www.leongold.net`), `SETUP_USER`/`SETUP_PASS`: the owner's login. Applied on every start (only rewritten when the stored password differs, so restarts keep devices signed in); surrounding quotes and spaces are ignored. The start log prints the username and password length to check them.

## Deploy (Liara)

- `liara.json`: Node 22 app `leon-gold` built in Iran (`build.location`, from Liara's own template), disk `data` mounted at `data`. `npm start` passes `--experimental-sqlite` so `node:sqlite` loads on any 22.x. Deploys automatically on every push to `main` (GitHub connected in the Liara panel).
- Then build the ledger with `-SyncUrl https://api.leongold.net` so the sync panel has the address filled in.
- First connection order matters: the phone (its data is the real one) connects first and seeds the empty server; other devices then take the server's copy (each downloads a backup of itself before replacing).

## Push notifications («حساب من»)

`notify.mjs`: Web Push with node:crypto only (VAPID ES256 key pair kept in the `meta` table under `vapid`; aes128gcm payloads). Table `push_subs` (endpoint, who=`party:<id>`, p256dh, auth). A party turns them on from its profile: `GET /api/portal/push/key`, `POST /api/portal/push/sub {endpoint, keys}` (only real push-service hosts: Apple, FCM, Mozilla, Windows), `/unsub {endpoint}`, `/test`. Events come from `push()`: a newly shown `vitrin` piece → every subscribed party; an order created or moved to a new step → its customer; an order item newly given to a party (`supId`, any kind) or a changed due date → that party. Messages to one party within `PUSH_DELAY_MS` (default 20 s) go as one. 404/410 from the push service forgets the subscription; signing a party out everywhere (new password, revoke, removed login) forgets its subscriptions. Tests: `test/notify.test.mjs` (a local push service decrypts what is sent; `PUSH_TEST_HOST` allows it).

The Android app (`../leon-gold-android`, 2026-11-14) has no Web Push in its WebView and many phones here have no Google push, so it fetches instead: with the portal token, `POST /api/portal/push/app {dev}` registers a device (table `app_devices`, 10 per party; answers `{last}`), `GET /api/portal/push/inbox?after=<id>` → `{items:[{id,title,body,url}], last}`, `POST /api/portal/push/app/off {dev}`. `flush()` keeps each message in `app_inbox` only for a party with an app device (last 50, 14 days). View `push_who` = everyone listening by either road; `tell()`, the vitrin loop and `nudges()` use it. `forget()` clears all three. Tests: `test/app-inbox.test.mjs`.

The ledger's own users («دفتر لئون», 2026-11-09) get them too: with the owner session, `GET /api/notify/key`, `POST /api/notify/sub {endpoint, keys, u}` (who=`ledger:<normalized ledger user>`; a new sign-in on the device takes it over), `/unsub {endpoint}`, `/test {endpoint}`. `notify.ledger()` sees every sync change to invoices, settlements, orders, expenses, parties, products, vitrin, targets (new / edit / delete; an order's new step) and tells every other ledger user whose «محدودیت» (settings/lock `perms`) includes that section; who did it comes from the `log` row in the same sync, and that user is skipped. A new `crm_leads` row (an order from «حساب من») goes to everyone who sees orders. Bursts per user go as one message (first 6 lines + «و n مورد دیگر»). The ledger asks right after sign-in (not in the profile); its sw.js shows them. Tests: `test/ledger-notify.test.mjs`.

## The public site on leongold.net (web.mjs, 2026-11-14)

GitHub Pages is slow or out of reach from Iran, so until the separate Liara static app exists (`../leon-gold-hosting`), this server also answers `leongold.net` (and sends `www` there) with `web/`: the site's static export built for the domain (`SITE_URL=https://leongold.net/`, sync `https://api.leongold.net`), the ledger at `/daftar/`. `/api/` on any host is still the API; `api.leongold.net` stays JSON only. Rebuild `web/` the hosting way (export build of the site's main + `offline/build.ps1 -Site web/daftar`) and commit it with the server. `SITE` (server.mjs) is still the GitHub address on purpose: «حساب من» logins and push subscriptions live on that origin until the real move.

- Downloads (2026-11-15): `apps/` beside `web/` is served at `https://leongold.net/apps/<name>` (.apk .exe .zip .dmg, plain names; `web.mjs`). The Android app is `apps/leon-gold.apk` (the site's download button points there). Rebuilding `web/` never touches `apps/`; a new APK = replace the file, commit, push (live server: owner's «تایید»).
